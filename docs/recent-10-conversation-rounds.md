## 第 1 轮

### 用户

所以review阶段，这个审查是不是也应该去开sub agent去做呢？这样在独立的上下文里面去review我当前的出来的这个Mock HTML或者是截图之类的。而且review阶段必须要截图才能去那个吗？直接看HTML是看不出这个视觉效果的，是吗？

### 助手

对，你这个 Skill 的最终 Review 应该使用一个独立、只读、干净上下文的 Subagent。但仅仅“开 Subagent”还不够——上一轮其实已经有独立审阅者，仍然误判了，因为它主要看了生成者挑选、滚动过的截图，没有自己从初始状态运行 HTML。

## HTML、截图和真实操作分别能看什么

| 证据 | 能发现 | 发现不了 |
|---|---|---|
| HTML/CSS/JS 源码 | 状态逻辑、死按钮、硬编码、语义、状态不一致 | 实际裁切、留白、层级、字体渲染、视觉呼吸感 |
| 渲染截图 | 视觉层级、密度、配色、对齐、截断、是否高级 | 点击后发生什么、焦点丢失、滚动重置、隐藏路径 |
| 真实操作 HTML | 可发现性、滚动、焦点、反馈、状态连续性 | 如果不保存关键画面，后续很难客观比较视觉变化 |

所以对于交互式 Mock，正确答案不是二选一，而是：

> 冻结 HTML + Reviewer 自己真实操作 + Reviewer 自己截取关键状态。

视觉 Review 必须看到渲染后的像素。只阅读 HTML，最多只能推测视觉效果，不能可靠判断呼吸感、比例、裁切和视觉层级。

但截图不应该只由生成者提供。生成者容易：

- 手动滚动到最漂亮的位置；
- 跳过难看的中间状态；
- 只截成功状态；
- 使用 Playwright 自动滚动，把不可发现的问题掩盖掉。

## 推荐的轻量 Review Pipeline

### 1. Builder 自检

生成 Subagent 完成 HTML 后：

- 跑一次核心路径；
- 做基础静态审计；
- 不给自己最终 `pass`。

### 2. 冻结候选

HTML 进入只读状态。Reviewer 获得：

- 原始用户需求；
- 用户审美偏好和明确反感项；
- 冻结的 HTML；
- 主视口；
- 核心任务路径。

Reviewer 不应该获得：

- Builder 的设计解释；
- 预期修正答案；
- “希望它通过”的暗示；
- Builder 挑选好的截图；
- 之前的评审结论，除非是在做明确的回归比较。

### 3. 独立 Reviewer 自己运行

Reviewer 必须从全新加载开始，自己操作：

1. 初始状态；
2. 第一次成功；
3. 关键阻塞或权限状态；
4. 渐进式披露；
5. 结果与恢复。

每次关键状态出现后，必须先在没有手动滚动的情况下检查：

- 当前发生了什么是否可见；
- 状态 owner 是否可见；
- 下一步是否可见；
- 是否被固定面板挡住；
- 是否需要猜测页面还能滚动。

这一步会直接发现我们刚才看到的 Permission 卡片问题。

### 4. Reviewer 自己截图

不需要规定死板的“三张、五张”，而是根据实际路径截图。至少覆盖：

- 默认首屏；
- 关键状态刚出现的 `first-seen state`；
- 主动展开信息后的状态；
- 结果或恢复状态。

如果页面存在 Dock、Focus Slot、固定底栏或多分栏，再内部增加一次短高度或窄窗口检查。这是 QA 证据，不是额外交付一个设计版本。

### 5. 三个非补偿性判断

同一个 Reviewer 可以依次检查三个方面，保持流程轻量：

- 产品与状态：任务、对象、状态、后果、恢复是否真实一致。
- 交互与可用性：发现性、焦点、滚动、反馈、键盘路径。
- 视觉与技术：层级、呼吸感、字体、密度、裁切、适配。

不能因为视觉好看，就抵消核心按钮不可见；也不能因为功能完整，就抵消视觉混乱。

### 6. 输出保持短

Reviewer 只返回：

- `pass` 或 `repair`；
- 最值得保留的设计决定；
- 最严重的 1–3 个可观察缺陷；
- 对应状态和截图证据。

然后由主 Agent 负责去重、修复和最终交付。

## 什么情况下必须开 Review Subagent

建议设为：

- 小型静态页面：Builder 自检即可，除非用户明确要求审美评审。
- 普通交互 Mock：一个独立 Reviewer。
- 多状态、权限、错误恢复、Dock/分栏：必须独立 Reviewer。
- 多个方向比较或 Skill Benchmark：Builder 与 Reviewer 必须分离；必要时产品审阅和视觉审阅并行。
- 只是改一个文案、颜色或小控件：不值得重新启动完整 Review。

你的 Mock HTML 通常包含交互、多状态，而且你非常关心高级感和用户体验，因此对这套 Skill 来说，“生成 Subagent + 一个独立 Review Subagent”应该成为默认路线。

最重要的修正不是简单增加“必须截图”，而是：

> Reviewer 必须自己渲染、自己操作、自己截取状态刚出现时的画面，不能只相信 Builder 提供的截图。

这样才能同时避免“只看源码看不出视觉”和“只看精修截图看不出真实使用问题”这两种误判。

## 第 2 轮

### 用户

OK，我我明我大致明白了。然后我顺便想问一下，我在做这个Skill的时候，为什么会出现了这么多的一些问题？这个是我的能力问题吗？是因为我下达的指令不对，还是因为我给的信息不太够？为什么花书他就能设出，他就能给出就是和AI共创出Design就是Design那个Skill呢？这里面到底是有什么gap？

### 助手

这不是你的能力问题，也不主要是你给的信息不够。更准确地说：你有不错的审美判断和产品直觉，但我们之前把“共同探索审美”误当成了“不断往提示词里补规则”，没有先搭建一套稳定的生成—验证系统。

你能连续发现裁切、认知负担、状态不真实、渐进披露失效，反而证明你的判断力是有效的。真正缺的是把这些判断编码成可复现机制——这是 Skill Engineering，不是普通用户本来就应该会的事情。

## 为什么会出现这么多问题

### 1. 你的部分要求最初确实比较抽象

例如：

- 高级感
- 呼吸感
- 安静克制
- 用户优先
- 对人友好

这些都是真实、重要的要求，但不是可以直接执行的 CSS 规则。模型可能把“呼吸感”解释成：

- 更大的留白；
- 更少的信息；
- 更大的标题；
- 更淡的颜色。

于是这次就出现了一个巨大营销式 Hero、固定空 Terminal 和被挤下去的主操作。

但这不代表你指令下错了。一个成熟 Skill 本来就应该把抽象目标翻译成可观察机制，比如：

> 呼吸感不是空白越多越好，而是当前任务拥有足够空间，固定区域不会挤压主操作，视线一次只承担一个主要判断。

这项翻译工作应该由 Skill 完成，不应该要求你提前像专业设计系统作者一样定义清楚。

### 2. 我们采用了“症状驱动补规则”

整个过程中基本是：

1. 出来太密；
2. 加“降低信息密度”；
3. 结果信息不够；
4. 加“最小充分信息”；
5. 结果信息被藏起来；
6. 加“渐进式披露”；
7. 结果内容虽然存在，却被滚动区挡住。

每次都在修上一次的症状，但没有先建立稳定的失败分类和验收案例。

这会产生 Skill 中常见的“沉积”：

- 规则越来越多；
- 模型自由度越来越低；
- 规则之间开始冲突；
- 模型把注意力花在满足提示词，而不是完成设计。

这也是为什么有时候不用 Skill，基础模型反而做得更好：它拥有较强的设计先验，而 Skill 给了它很多抽象限制，却没有提供足够强的正向视觉锚点和确定性验证工具。

### 3. 我们把“设计生成”和“设计验证”混在了一起

Builder 自己生成、自己操作、自己截图、自己宣布通过，天然会出现盲区。

更严重的是，Playwright 自动把按钮滚进视口，使 Builder 以为“按钮能点击，所以没问题”；然后它又把滚动后的漂亮状态截下来。独立 Reviewer 看到这些截图，也容易误判。

所以这次失败不是缺一句“不要裁切”，而是缺：

- first-seen state 验证；
- 独立 Reviewer 自己运行 HTML；
- 滚动与焦点连续性检查；
- 状态投影一致性检查。

### 4. 我们试图一次覆盖过大的范围

你希望它同时支持：

- 桌面端；
- Web；
- App-like surface；
- 零到一项目；
- 有真实产品上下文的改版；
- 单方案；
- 多方向探索；
- 静态画面；
- 可点击交互；
- 可播放流程；
- 高级视觉审美；
- 产品状态真实性。

这是一个非常大的问题空间。

我们当前候选只有：

- 12 个文件；
- 4 个评测案例；
- 149 行核心 Skill；
- 少量资产和脚本。

它还不足以覆盖这么大的分布。不是核心 Skill 一定要继续变长，而是需要更完整的按需参考、正向样例和测试集。

## 但花叔也不是完美答案

不能把它理想化。

例如，它当前的验证脚本主要做：

- 打开 HTML；
- 截图；
- 检查控制台；
- 多视口截图。

[verification.md](/Users/edy/git/huashu-design/references/verification.md:9) 对交互验证甚至主要建议用户自己点击。它没有系统验证：

- 状态刚出现时是否可见；
- 展开后滚动是否重置；
- 焦点是否丢失；
- Badge、Rail、主卡片状态是否一致；
- Builder 是否用手动滚动美化截图。

所以花叔可能更容易产出第一眼漂亮的静态画面，但我们现在追求的是：

> 第一眼好看 + 核心用户流程正确 + 多状态真实 + 可恢复 + 可操作。

这比单纯生成漂亮 HTML 难一个层级。

它还有其他明显代价：

- 527 行主 Skill，本身很重；
- 强制三方向会增加时间和成本；
- 只有 6 个明确测试 Prompt，[test-prompts.json](/Users/edy/git/huashu-design/test-prompts.json) 也不是完整的自动化 UI 回归系统；
- 仓库自己专门写了弱 Runtime 降级，说明完整流程确实可能导致上下文爆炸和偷工。

## 真正的 Gap 是什么

不是：

> 花叔会设计，而你不会。

而是：

> 花叔已经把大量审美经验、失败案例、正向样例、组件资产和流程工具产品化；我们还处于把你的隐性判断逐渐提炼出来的阶段。

你现在已经提供了最难获得的那部分：

- 真实任务；
- 真实失败案例；
- 你明确喜欢和反感的结果；
- 对用户行为优先级的判断；
- 对“呼吸感”“高级感”“渐进披露”的逐步澄清。

接下来缺的是工程化：

1. 从你过去的 Session 建立 6–8 个稳定 Golden Cases。
2. 保存少量你接受和拒绝的真实画面，作为正向/反向证据。
3. 核心 Skill 只保留方法和路由，不继续堆规则。
4. 增加少量高质量视觉方向参考与 Showcase，而不复制整个花叔风格库。
5. Builder 与 Reviewer 分离。
6. Reviewer 必须自己运行 HTML、截图和检查 first-seen state。
7. 用运行时验证解决裁切、焦点、滚动和状态一致性，而不是继续用文字提醒模型。

所以这段过程并不是“你没能力把 Skill 做好”，而是在进行必要的需求发现。真正的问题是我们此前太早把每轮反馈写进 Skill，却太晚建立评测系统。下一阶段应该从“继续补提示词”切换成“先建立 Golden Cases、正向样例和独立运行时 Review”。这才是从实验性 Skill 走向成熟设计系统的分水岭。

## 什么是 Leading Concept？

它不是“按钮圆角 8px”这类局部规则，而是一个能指导模型处理一整类未知问题的上位概念。

花叔 Skill 里的具体例子：

- [从 existing context 出发](/Users/edy/git/huashu-design/SKILL.md:78)：设计应从现有产品、品牌和资产长出来，避免通用 AI 页面。
- [Junior Designer 模式](/Users/edy/git/huashu-design/SKILL.md:103)：尽早暴露假设，降低方向理解错误的成本。
- [给 variations，不给最终答案](/Users/edy/git/huashu-design/SKILL.md:112)：审美存在不确定性时，用本质不同的方向帮助决策。
- [系统优先，不要填充](/Users/edy/git/huashu-design/SKILL.md:124)：每个元素必须“挣得”自己的位置，不能为了填满屏幕而堆数字、图标、渐变。
- [反 AI slop](/Users/edy/git/huashu-design/SKILL.md:131)：不是机械禁止紫色或圆角，而是防止产品被训练数据里的“平均视觉”稀释掉。

它们之所以是 “leading”，是因为模型遇到规范里没写过的新情况时，仍能据此做判断。

不过不能原样全抄。例如你明确不想经历“初稿确认—再实现—再确认”，所以我没有把 Junior Designer 多轮确认设为强制流程；variations 也只在用户要求不同方案或存在重大方向不确定性时启用。

## 这次写进 Skill 的四个概念

更新后的 [SKILL.md](/Users/edy/.codex/skills/design-mock-html-directions/SKILL.md:48) 主要新增：

- `first-seen state`：关键操作发生后，不滚动也能看到发生了什么、归谁负责、下一步或恢复方式。
- `earned chrome`：侧栏、底栏、空面板必须有当前价值；否则折叠、缩小或延后，不能挤掉主任务。
- `local reveal`：详情在所属对象附近展开，不能把用户瞬移到别处，也不能丢失焦点或滚动位置。
- `canonical truth`：Rail、主区、Focus Slot、结果提示都必须投影同一份状态，不能各说各话。

独立审查规则也已修正：[design-judgment.md](/Users/edy/.codex/skills/design-mock-html-directions/references/design-judgment.md:7)。Reviewer 必须亲自打开、点击并截取 first-seen 状态，不能拿生成者挑选的截图当证明。

## 他有效利用 AI 的关键

- AI 把真实事故提炼成规则；
- AI 帮助压缩和重构 Skill；
- 最终取舍仍由人决定。

也就是说，AI 是放大器、执行者和批评者，但花叔本人仍然是审美与产品判断的“裁判”。

你前面的过程里，生成者、裁判、方法论作者和项目经理经常都是同一个 AI。它会天然倾向于证明自己上一轮提出的方法有效，所以容易不断增加流程。

## 真正的模糊地带

可以把 UI 质量分成三层。

### 可以客观验证

这些适合写成硬规则：

- 内容有没有裁切；
- 控件能不能点击；
- 状态是否一致；
- 主路径是否可达；
- 反馈是否及时；
- 焦点、滚动是否跳动；
- 错误后能否恢复；
- 窄窗口是否溢出。

上一轮独立 Reviewer 抓到的状态机、unread、resume、遮挡问题都属于这一层。

### 可以用方法论提高概率

这些适合少量 leading concepts，而不是几十条硬规则：

- 信息层级；
- 渐进披露；
- 认知负担；
- first-seen state；
- earned chrome；
- local reveal；
- 产品特异性；
- 安静、克制、呼吸感。

它们可以帮助模型判断，但不能机械保证结果。

### 无法由 Skill 客观保证

这些最终仍需要人判断：

- 是否“高级”；
- 是否“惊艳”；
- 哪种比例最优雅；
- 哪个字体组合最有气质；
- 创新程度是否刚刚好；
- 某个获奖风格是否适合当前产品。

Skill 可以帮助模型找到参考、避免平庸、输出几个方向，却不能把“高级感”编译成确定程序。

## 你为什么会觉得一直不在正确道路上

核心原因是，我们一度在做这件不可能完成的事：

> 试图先完整定义“什么是好设计”，然后要求 Skill 每次自动生产好设计。

但更合理的目标应该是：

> Skill 保证模型使用一个可靠、轻量的设计过程，同时给视觉构图保留足够自由；最终审美由作品比较和人的选择决定。

另外还有几个具体偏差：

- 用同一类高密度 Electron 工作台反复测试，容易把“通用 Skill”过拟合成桌面 IDE Skill。
- 把候选 HTML 的实现 Bug 误判成 Skill 方法论缺陷，于是不断向 Skill 增加规则。
- 每发现一个问题就写一条规则，形成 sediment：规则越来越多，模型自由度越来越低。
- 你说“感觉不对”，AI 会努力替你发明一个解释；这个解释听起来专业，但不一定就是根因。
- 我们花了很多时间优化验证流程，却没有始终区分“设计质量”与“验证质量”。验证只能发现失败，不能自动创造审美。

## 这不是你的能力差，而是你缺少一个稳定的“裁判接口”

其实你已经表现出相当明确的判断：

- 讨厌黑色 AI 工具背景；
- 讨厌信息同时铺满；
- 重视普通用户的第一使用路径；
- 喜欢温暖、克制、干净；
- 不接受漂亮截图掩盖真实交互；
- 希望看到本质不同的方向；
- 认为视觉风格必须从产品上下文长出来。

你不是“没有品味”，而是你的品味目前更多以“看到作品后能判断”存在，而不是能提前写成形式化规范。

这很正常。审美通常更适合通过成对比较学习：

> A 和 B，我更喜欢哪一个？为什么？

而不是从零回答：

> 请完整定义什么是高级感。

## 接下来更正确的边界

这个 Skill 最终只需要承担四件事：

1. 找上下文或现实参照。
2. 理解用户和第一次成功。
3. 给模型较高自由度生成。
4. 实际运行、截图并检查明显失败。

其中：

- 可测试的问题做硬验证；
- 产品和用户问题使用少量 leading concepts；
- 审美问题使用参考、方向对比和你的最终选择；
- 单次实现 Bug 修 HTML，不自动升级为 Skill 规则；
- 同一失败在多个不同案例重复出现，才考虑写回 Skill。

所以真正应该追求的不是：

> 这个 Skill 能不能保证每次做出 90 分 UI？

而是：

> 它能不能稳定避免明显失败，同时比不用 Skill 更容易产出有上下文、有用户路径、有产品性格的候选方案？

这才是一个现实、可验证，也不会把模型创造力压死的目标。

# 假设我是花叔，我会这样做

## 第一阶段：我不会先让 AI 写 Skill

我会先对 AI 说：

> 我不是要你现在写 Skill。  
> 这里有我过去认可的 5 个作品、不认可的 5 个作品，以及真实交付过程。  
> 请找出：我反复坚持了什么、反复拒绝了什么、哪些步骤是创作自由、哪些步骤不能出错。  
> 不要补充通用设计原则。

这一步非常重要。

花叔仓库第一次提交时，就已经包含：

- 445 行 `SKILL.md`

- 浏览器、macOS、iOS 等组件资产
- 大量 showcase HTML 和截图
- 动画、幻灯片、设计画布等实现

说明他不是面对一张白纸问 AI：

> 请告诉我什么是好设计。

而是已经有相当多的作品、偏好和制作经验，再让 AI 将它们结构化。

你以后也应先准备一个很小的“证据包”：

```text
3 个你满意的真实结果
3 个你不满意的真实结果
3 个典型任务
3 条绝对不能发生的事情
1 条你认为最重要的核心哲学
```

不需要先写方法论。

## 第二阶段：让 AI 从案例中蒸馏，而不是自由发明

模拟对话：

> 花叔：根据这些案例，提取最多 5 个能够解释多数选择的核心概念。不要给我 30 条 UI 检查项。  
>   
> AI：existing context、Junior Designer、variations、system over filler、anti-slop。  
>   
> 花叔：现在逐个证明。指出每个概念解释了哪些案例。解释不了案例的概念删除。

这就是 leading concepts 的来源。

不是先想一个听起来漂亮的词，再往里面填内容，而是：

```text
多个真实判断
    ↓
发现重复模式
    ↓
给模式起一个模型容易理解的名字
    ↓
让这个名字代替十几条重复规则
```

因此，未来不要问 AI：

> 这个 Skill 还需要哪些原则？

应该问：

> 这 8 个真实案例里，哪些判断发生了至少 3 次？能否用一个已有概念统一解释？

前一种问法必然导致规则膨胀，后一种才会得到有效抽象。

## 第三阶段：先写最小 v0，不追求完整

我会告诉 AI：

> 现在写一个最小 Skill，只包括：
>
> - 什么时候触发；
> - 输入是什么；
> - 核心流程；
> - 3～5 个核心概念；
> - 什么算完成。
>
> 暂时不要建风格库、评分系统、复杂脚本和完整异常处理。

v0 的目的不是“设计出完美系统”，而是产生一个可以被证伪的假设：

> 加入这个 Skill 后，模型是否更稳定地采用我认可的工作过程？

注意不是：

> 它能不能每次产出同样好看的作品？

Skill 首先追求的是过程可预测，而不是结果完全一致。

## 第四阶段：基线和 Skill 同题比较

模拟花叔的做法：

> 花叔：选 5 个固定题目。  
> A 组不用 Skill，B 组使用 Skill。  
> Builder 互相不知道对方结果。  
> Reviewer 不知道哪个用了 Skill。  
> 比较它们，不要给绝对分数。

他仓库里后来明确出现了：

- 6 judge；
- 5 轮盲测；
- 双 judge 盲评；

1. 最常见的正常任务；
2. 一个信息不足或零到一任务；
3. 一个容易触发该 Skill 典型失败的任务。

每次修改后，都用相同题目比较：

```text
不用 Skill 的结果
旧 Skill 的结果
新 Skill 的结果
```

只要这样就足够了。

## 第五阶段：先判断“这是谁的错”

Reviewer 发现问题后，我不会马上改 Skill，而会先要求 AI 分类：

> 这个失败属于哪一类？
>
> 1. 单个候选实现 Bug；
> 2. 用户需求或上下文不足；
> 3. 模型偶发失误；
> 4. Skill 缺少关键指令；
> 5. Skill 中现有规则反而导致了失败；
> 6. Reviewer 的判断没有可靠依据。

只有第 4、5 类适合修改 Skill。

我们前面最大的浪费之一，是经常这样：

```text
发现 Mock 有一个问题
    ↓
认为 Skill 不完整
    ↓
添加新角色、新阶段、新规则
    ↓
Skill 更重
    ↓
模型自由度下降
```

正确路径应该是：

```text
发现问题
    ↓
先修候选
    ↓
在其他任务里再次出现？
    ├─ 没出现：候选 Bug，不进 Skill
    └─ 重复出现：才考虑修改 Skill
```

## 第六阶段：每次只做最小修正

模拟指令：

> 花叔：不要重写 Skill。  
> 这个失败只说明“品牌事实未经核实”。  
> 请找出它应该修改的唯一上游位置。  
> 优先用一个 leading concept 或 completion criterion 修复。  
> 不允许新增三个文件来解决一个问题。

花叔仓库里能看到这种演化：

- 先增加“事实验证先于假设”；
- 然后增加“品牌资产协议”；
- 再同步到工作流和反 slop；
- 真实交付暴露问题后继续补小缺口。

有效的修正通常有三种：

- 加一个更好的上位概念；
- 加一个可验证的完成条件；
- 对脆弱机械步骤增加脚本。

而不是默认增加 Reviewer、Schema 或新 Pipeline。

## 第七阶段：让 AI 负责盲审，但不让它决定品味

我会这样分工：

### Builder

看到 Skill、用户需求和必要上下文，负责生成。

### Functional Reviewer

亲自运行产物，检查：

- 能否完成；
- 状态是否一致；
- 是否裁切；
- 是否有错误；
- 恢复是否有效。

### Taste Reviewer

只看作品和原始需求，判断：

- 是否有产品性格；
- 是否像训练数据平均值；
- 注意力是否明确；
- 哪一个方案更值得保留。

### 人

最后决定：

- 我喜欢哪个；
- 哪个判断可以成为长期原则；
- 哪条规则值得进入 Skill；
- 什么时候停止。

AI Reviewer 能够发现大量问题，但它们共享相似的训练分布，所以“多个 AI 都说好看”也不等于真的好看。

## 第八阶段：定期让 AI 删除，而不是继续增加

花叔在 2026-07-01 的提交里做过：

- 去冗余；
- 检查点统一；
- 路由前移；
- 把 652 行压缩到 500 行；

这非常关键。

成熟 Skill 不是越写越长，而是经历：

```text
真实事故 → 加规则
规则增多 → 找重复
多个规则 → 折叠为 leading concept
细节规则 → 移到 references
机械步骤 → 变成 scripts
无效规则 → 删除
```

每隔几轮，你都应该让 AI 做一次“删除审查”：

> 对 Skill 逐句做 no-op test：
>
> - 删除这句话，模型行为会变化吗？
> - 它是否和别处重复？
> - 它是否只是听起来正确？
> - 它只适用于一个历史案例吗？
> - 它应该在核心 Skill、Reference，还是根本不应该存在？
>
> 本轮目标是减少行数，不得新增能力。

# 你以后制作任何 Skill 的通用流程

可以固定使用下面这套八步。

## 1. 定义行为差异

先写一句：

> 不使用这个 Skill 时，AI 通常会做什么；使用后，我希望它稳定改变什么？

例如：

```text
不用时：直接从零生成通用 UI。
使用后：先判断现有上下文，再保护主路径，同时保留视觉构图自由。
```

如果这句话说不清，暂时不要写 Skill。

## 2. 收集案例

至少准备：

- 3 个正常任务；
- 2 个边界任务；
- 2 个好结果；
- 2 个坏结果。

## 3. 让 AI 提取重复判断

只允许提取案例中确实存在的模式，不得自由补齐完整理论。

## 4. 写最小 v0

只写：

- Trigger；
- Workflow；
- Leading concepts；
- Completion criteria；
- Non-goals。

## 5. 固定三道题

同题比较：

- 无 Skill；
- 当前 Skill；
- 修改后 Skill。

## 6. 独立审查

Reviewer 不知道：

- 你希望哪个版本赢；
- 预期缺陷是什么；
- Builder 的解释是什么。

## 7. 分类失败

先区分：

- 候选 Bug；
- Skill Bug；
- 上下文问题；
- 审美偏好；
- 随机波动。

同类问题重复出现，才进入 Skill。

## 8. 定期压缩

每增加三次规则，至少做一次删除和合并。

# 以后可以直接复制使用的 AI 指令

## 创建新 Skill 前

```text
我正在考虑制作一个 Skill，但现在不要写 SKILL.md。

这是我提供的真实任务、好结果、坏结果和历史操作过程。

请分析：
1. 不使用 Skill 时，模型的默认失败是什么；
2. 哪些判断在多个案例中重复；
3. 哪些属于创作自由；
4. 哪些属于不可出错的机械步骤；
5. 哪些信息目前不足，不能可靠抽象。

不得补充案例中不存在的通用最佳实践。
```

## 写 v0

```text
基于已确认的案例，写最小可测试 v0。

约束：
- 核心流程不超过 5 步；
- leading concepts 不超过 5 个；
- 每一步都有可观察的完成条件；
- 创作性部分保持高自由度；
- 脆弱机械步骤才允许低自由度；
- 不创建暂时用不到的 references、scripts 或框架。
```

## 测试结果后

```text
先不要修改 Skill。

把这次失败分类为：
- candidate implementation bug
- missing task context
- stochastic model failure
- skill omission
- harmful skill constraint
- unsupported reviewer preference

给出证据。只有 skill omission 或 harmful constraint 才允许提出 Skill 修改。
```

## 修改 Skill

```text
提出能够修复该重复失败的最小修改。

优先级：
1. 修改 completion criterion；
2. 用 leading concept 合并重复规则；
3. 修改已有一句话；
4. 移动到按需 reference；
5. 最后才新增流程或文件。

不得借机处理其他未复现的问题。
```

## 定期清理

```text
对当前 Skill 做删除优先的审查。

找出：
- duplication
- no-op
- sediment
- sprawl
- 只服务一个历史案例的规则
- 已经可以由模型默认能力完成的解释

目标是减少上下文负担，同时保持已验证行为。
```

# 一、先看花叔到底在做什么

假设我是花叔，我不会说：

> AI，帮我写一个很厉害的 Design Skill。

我会这样想：

> AI 本来已经会写 HTML，也知道 CSS、React、Apple HIG、Material Design。  
> 我没必要再教它这些。  
> 我要解决的是：它明明会做，为什么做出来还是经常很普通、很假、很像 AI？

所以一个 Skill 最重要的问题不是：

> 我要把哪些知识写进去？

而是：

> 模型已经会什么？它在什么地方明明会，却总是做错？

花叔 Skill 里的绝大多数重要规则，都能还原成这个结构：

```text
真实翻车
→ 找到模型为什么会翻车
→ 判断应该在哪一层拦截
→ 用最便宜的方式拦截
```

这里最值得你学的，不是他的 UI 规则，而是他如何给不同问题选择不同的“控制手段”。

# 二、花叔不是把所有问题都写成 Prompt

这是最核心的判断。

花叔实际上使用了至少七种不同手段：

| 问题类型 | 花叔用什么解决 |
|---|---|
| 模型方向从根上错了 | 核心哲学 |
| 只有特定任务才需要 | 路由和 Reference |
| 用户必须亲自决定 | 三方向＋停下来等选择 |
| 容易被模型跳过 | Gate 文件 |
| 重复、机械、容易写错 | Script 或 Asset |
| 需要检查结果 | Verification |
| 审美没有唯一答案 | 多个真实方案比较 |

这比“把所有建议都加进 SKILL.md”高级得多。

# 三、案例一：为什么“existing context”是核心哲学

花叔写的是：

> 好的 hi-fi 设计一定从已有上下文长出来。凭空做 hi-fi 是 last resort。

见 [SKILL.md](/Users/edy/git/huashu-design/SKILL.md:78)。

你先想：这句话解决的到底是什么？

表面看，是“先读 Design System”。

实际上，它解决的是一个模型级默认行为：

```text
用户说：做一个 SaaS 页面
模型脑中：SaaS = 深色背景 / 圆角卡片 / 渐变 / Dashboard
```

模型会自动从训练数据的“类别平均值”开始。

花叔判断：

> 这个问题不是少了一条颜色规则。  
> 而是模型选错了信息来源。

于是他没有写：

- 背景应该是什么颜色；
- 卡片用什么圆角；
- 字号多少；
- 要有多少留白。

他把“设计决策的数据源”改了：

```text
错误数据源：模型训练中的 SaaS 平均值
正确数据源：用户产品、代码、品牌、截图、真实资产
```

这就是为什么它够资格成为核心哲学。

### 通用判断

以后你做任何 Skill，都先问：

> 这个任务中，AI 最容易使用哪个错误的信息来源？

例如：

- 写技术文档：AI 容易凭记忆，而不是读当前代码；
- 做法律分析：AI 容易凭一般法理，而不是读具体辖区和最新法规；
- 做代码 Review：AI 容易只看 Diff，不看调用链；
- 做 UI：AI 容易使用产品类别平均值，不读真实产品。

如果问题是“模型从一开始就看错地方”，应该写成上位原则，而不是补几十条细节。

# 四、案例二：为什么事实验证被放在原则 #0

花叔曾经遇到一个真实事故：

> 用户要做 DJI Pocket 4 发布动画，AI 凭记忆认为产品没有发布，于是做了一个假的概念剪影。实际上产品已经发布，官方素材也存在。

见 [SKILL.md](/Users/edy/git/huashu-design/SKILL.md:44)。

花叔没有把这个问题总结成：

> 做 DJI 时记得搜索 Pocket 4。

因为这只能修一个案例。

他问的是：

> 这个事故里，真正可以复用的失败模式是什么？

答案是：

```text
AI 对时间敏感事实使用了训练记忆
```

所以抽象为：

> 事实验证先于假设。

然后他继续把它做成可执行流程：

1. WebSearch；
2. 找权威来源；
3. 核实存在性、版本和规格；
4. 写入 `product-facts.md`；
5. 找不到就问用户。

注意，这里有三层设计：

### 第一层：Leading concept

`事实验证先于假设`

让模型理解为什么做。

### 第二层：触发条件

- 新产品；
- 新版本；
- 发布状态；
- 自己想说“我记得好像……”的时候。

让模型知道何时做。

### 第三层：外部产物

`product-facts.md`

让事实不依赖模型在长上下文中的记忆。

### 通用判断

一个规则应该有三部分：

```text
为什么 → 什么时候 → 做完留下什么证据
```

如果只有“为什么”，它容易成为口号。

如果只有“做什么”，模型会机械执行但不会处理边界。

如果没有证据，长会话里它会认为自己“应该做过了”。

# 五、案例三：为什么品牌问题不是靠“反 AI slop 清单”解决

花叔写了很多反 slop 条目：

- 不要默认紫渐变；
- 不要 Emoji 当图标；
- 不要黑底霓虹；
- 不要手画假的产品 SVG。

但他真正认为最重要的，不是这张禁止清单，而是：

> 资产 > 规范。

见 [SKILL.md](/Users/edy/git/huashu-design/SKILL.md:84)。

为什么？

假设你告诉 AI：

```text
不要紫渐变
不要黑色背景
不要 Emoji
不要圆角卡片
```

模型可能做出一个米白色、衬线字体、细边框页面。

看起来不那么 AI 了，但它仍然可能和产品毫无关系。

花叔的判断是：

> “不像 AI”不是目标，“像这个产品”才是目标。

所以他把解决方案分成正反两面：

### 反面：不要做什么

反 slop 清单。

### 正面：应该从哪里获得身份

- 官方 Logo；
- 产品图；
- UI 截图；
- 品牌字体；
- 真实文案；
- 真实颜色；
- 已有组件。

这就是一句很重要的通用判断：

> 负面清单只能防止模型落到最差答案，不能告诉模型正确答案从哪里来。

以后任何 Skill 都一样。

例如做代码 Skill：

```text
负面规则：不要写 any，不要吞异常，不要重复代码
```

只能防止烂代码。

真正的正向来源应该是：

```text
现有架构、相邻模块、项目约定、测试模式、领域模型
```

所以你的 Skill 不能只有“不要什么”，还必须告诉模型：

> 正确答案应该从哪里长出来。

# 六、案例四：为什么花叔一定给三个方向

这部分不能简单理解成“多出几个方案比较好”。

花叔其实在解决一个权限问题：

> 审美方向到底应该由 AI 决定，还是由用户决定？

例如用户说：

> 做 Apple 风格。

AI 可能认为这已经很明确。

但花叔认为：

```text
Apple 风格
├─ 深空暗场
├─ 大白底衬线
├─ 产品色沉浸
└─ 工业材料特写
```

“Apple”只是一个语境，不是一个确定设计。

所以他得出一句非常具体的判断：

> 风格词收窄解释空间，但不转移选择权。

见 [SKILL.md](/Users/edy/git/huashu-design/SKILL.md:185)。

这句话很有价值，因为它分清了两件事：

- AI 可以探索可能性；
- 用户拥有审美选择权。

为什么必须出真实视觉，而不是文字描述？

因为用户面对：

- editorial；
- refined；
- neo-brutalism；

这些词根本无法可靠判断。

但看见三个 HTML 截图后，用户可以说：

> 我要第二版的布局，加第一版的配色。

所以花叔写了：

> 选择只有在看见真实视觉之后才有效。

### 他使用的三种探索方式也不是随便选的

#### 1. 秒数轮盘

随机选风格。

目的不是寻找最佳答案，而是打破模型永远选择安全极简的惯性。

#### 2. 现实获奖案例

目的不是复制，而是把质量标准锚定在真实作品上，避免模型自己想象“高级”。

#### 3. 最适合的设计师

利用模型训练中对设计师哲学的已有知识，寻找最贴合内容的定制方向。

这三种方向分别解决：

```text
轮盘：对抗模型惯性
获奖案例：建立现实质量锚点
设计师：寻找内容与哲学的匹配
```

这才叫“本质不同”，不只是三套颜色。

### 通用判断

什么时候应该让 AI 自动决定？

- 可逆；
- 低成本；
- 有明确正确答案；
- 用户不需要表达偏好。

什么时候必须让用户决定？

- 主观；
- 高返工成本；
- 多个答案都合理；
- 决定会改变后续大量工作。

所以以后制作 Skill，可以问：

> 这个流程里，哪些决定 AI 有资格做，哪些决定必须还给用户？

这比“要不要 Subagent”更根本。

# 七、案例五：为什么三个 Subagent 使用同一份 Spec 和资产

花叔要求：

- 三个 Subagent 使用相同内容；
- 使用相同图片；
- 使用相同尺寸；
- 互相看不到对方结果；
- 只改变设计逻辑。

这是一个真正的对照实验。

如果三个版本分别使用：

- 不同文案；
- 不同信息结构；
- 不同图片；
- 不同尺寸；

用户最后不知道自己喜欢的是视觉方向，还是只是某一版图片更好。

所以他先写一份共同 Spec，然后只改变一个变量：

```text
固定：
- 用户
- 内容
- 图片
- 品牌
- 尺寸
- 目标

改变：
- 设计逻辑
```

### 通用判断

当你让 AI 比较多个方案时，要先问：

> 哪些变量必须固定，才能知道差异到底由什么造成？

这适用于所有 Skill：

- 比较三种代码架构：需求和测试必须固定；
- 比较三种文案：产品事实和受众必须固定；
- 比较三种研究方法：研究问题和数据必须固定；
- 比较三种 UI：内容、状态和尺寸必须固定。

否则“多个方案”只是多个随机结果，不是有效实验。

# 八、案例六：为什么有 Gate 文件，而不只是提醒 AI

花叔发现：

> 长会话里，即使 Skill 写了“等待用户确认”，模型看到用户说“继续”后，也可能直接跳过方向确认，开始渲染 210 秒长片，最后整片返工。

于是他没有继续加一句：

> 再次提醒：一定要确认。

因为模型不是“不知道”，而是“会忘、会自我解释、会被上下文惯性冲过去”。

所以他增加：

- `brand-spec.md`
- `direction-approved.md`
- `导演稿.md`

见 [SKILL.md](/Users/edy/git/huashu-design/SKILL.md:344)。

然后规定：

```text
文件不存在 = 该步骤没完成
```

甚至给长视频渲染加 Hook，没有 Gate 文件就不允许运行。

这是把自然语言约束变成外部状态。

### 通用判断

遇到模型“知道但总跳过”的问题，不要继续加强措辞。

问：

> 能不能把它变成一个机器可观察的状态？

例如：

| 任务 | Gate |
|---|---|
| 数据库迁移 | `migration-plan.md` |
| 发布生产环境 | 测试报告＋审批记录 |
| 做品牌设计 | `brand-spec.md` |
| 修改 API | compatibility checklist |
| 大规模重构 | baseline tests 必须先变绿 |
| 危险命令 | dry-run 输出存在 |

自然语言只能劝模型，Gate 才能阻止模型。

# 九、案例七：为什么重复机械问题要变成 Asset 或 Script

花叔有：

- `ios_frame.jsx`
- `deck_index.html`
- `cursor.jsx`
- `verify.py`
- `fetch_images.py`
- 视频渲染和校验脚本

例如 iOS Device Frame。

AI 每次自己手画 Dynamic Island，理论上都会，但经常：

- 宽度不对；
- 状态栏撞位；
- Home Indicator 错；
- 窄屏崩掉。

这类问题不是审美判断，而是重复机械实现。

所以花叔直接规定：

> 不要再思考，使用已有 Asset。

### 通用判断

当一个问题满足下面条件：

- 正确答案相对固定；
- 重复出现；
- AI 每次重写都有概率出错；
- 创造性没有价值；

就不应该继续写 Prompt，而应该提供脚本、模板或组件。

一句大白话：

> 需要创造的地方让 AI 创造，不值得创造的地方不给它创造机会。

这是制作 Skill 最重要的自由度判断。

# 十、从这些案例抽象出的通用判断模型

以后你发现一个 Skill 问题，不要直接问：

> 要不要把它写进 Skill？

先用下面六问判断。

## 第一问：这是一次 Bug，还是模型稳定的默认倾向？

- 只出现一次：先修产物。
- 不同任务反复出现：才考虑 Skill。

## 第二问：问题是“看错信息”，还是“不会执行”？

- 看错信息：改来源原则，例如 existing context。
- 不会执行：补 Reference、Example 或工具。

## 第三问：这是客观错误，还是合理答案之间的选择？

- 客观错误：验证、脚本、Gate。
- 多个合理答案：给方向，让用户选。

## 第四问：这条规则对所有任务成立吗？

- 所有任务成立：核心 Skill。
- 特定类型成立：路由到 Reference。
- 特定项目成立：留在项目上下文，不能写进通用 Skill。

## 第五问：模型是“不知道”，还是“知道但会跳过”？

- 不知道：补知识或示例。
- 知道但跳过：增加完成条件、外部文件或硬 Gate。

## 第六问：这里的自由发挥有价值吗？

- 有价值：只规定目标，不规定实现。
- 没价值：模板化、脚本化、固定化。

可以压缩成一张决策表：

| 失败本质 | 应该用什么 |
|---|---|
| 错误信息来源 | Leading concept |
| 条件性知识缺失 | Reference |
| 重复机械错误 | Script / Asset |
| 步骤容易被跳过 | Gate / completion criterion |
| 主观但多个答案合理 | Variations＋用户选择 |
| 一次实现错误 | 只修产物 |
| 环境能力不同 | Runtime degradation |
| 结果无法观察 | Render / screenshot / operate |

这才是你以后做其他 Skill 真正应该复用的模型。

# 十一、用你的 Mock HTML Skill 跑一次这套判断

例如我们发现：

> 页面主信息显示不完整。

先不要立即添加“高级 UI Reviewer”。

使用六问：

### 1. 是一次 Bug，还是稳定倾向？

如果只有一个 HTML 裁切，是候选 Bug。

如果不同任务里都出现固定 Bottom Panel 挤掉主任务，才说明存在稳定倾向。

### 2. 原因是什么？

不是模型“不懂高级感”。

而是它没有优先保证当前任务的空间，固定 Chrome 又不会主动退让。

### 3. 这是客观还是主观？

裁切是客观错误，可以检查。

### 4. 应该放哪层？

不该写：

> Bottom Panel 高度不得超过 145px。

这只适用于一个布局。

应该抽象为：

> `earned chrome`：常驻区域必须证明当前价值，否则折叠或让出空间。

### 5. 如何验证？

不是让 Reviewer 阅读 HTML 源码。

而是：

- 打开页面；
- 截图；
- 不滚动；
- 看 owner 和 next action 是否可见；
- 做紧凑高度探针。

### 6. 要不要脚本化？

截图、viewport、bounding box 可以脚本化。

“是否安静克制”不能完全脚本化，仍由人判断。

这就是一条规则如何正确长出来。

---

# 十二、花叔 Skill 也有明显问题，不要把它当圣经

这点我必须告诉你，否则你还会继续被它牵着走。

## 1. “Fallback”已经不是真正的 Fallback

它一边说：

> 有 Context 就从 Context 长出来，不要套库。

一边又规定：

> 任何新设计 100% 必须出三方向。

这实际上已经从“没有上下文时的兜底”变成一个强制产品流程。

它可能适合花叔的工作方式，但不一定适合你。

## 2. 流程非常重

每个网页方向都做完整 HTML，三个方向就是三份实现。

对品牌宣传片可能合理；对一个小型 Mock 可能成本失控。

## 3. 测试已经出现陈旧

`test-prompts.json` 里：

- 10 页 Deck 仍期待 `deck_stage.js`；
- 当前 Skill 默认却更偏向 `deck_index.html` 多文件结构。
- Habit Tracker 测试仍期待询问 overview/flow；
- 当前 Skill 已改成默认平铺且可操作，不再询问。

说明它也有 sediment，测试和规则会漂移。

## 4. Verification 对真实交互仍不够强

它的 `verify.py` 主要负责：

- 打开；
- 截图；
- Console error。

对于复杂交互，它甚至写的是“建议让用户自己点一遍”。

所以花叔 Skill 在视觉生产、Deck、动画、品牌资产上很强，不代表它已经完整解决复杂产品交互验证。

## 5. 数值审美规则有假精确

例如：

- 标题至少正文 2.5 倍；
- 留白至少 40%；
- 颜色不超过 3～4 种。

这些适合作为 Reviewer 提醒，不适合成为所有设计的硬规则。

所以你该学习的是：

> 花叔如何把真实失败放到正确的控制层。

而不是复制他的每一条规则。

# 十三、导师给你的最终作业

以后你想做一个新 Skill，先不要让我写。

你先回答下面七句话：

```text
1. 这个 Skill 不存在时，AI 最稳定的默认错误是什么？
2. 正确答案应该从哪里获得，而不是从模型平均值获得？
3. 哪些决定有客观答案？
4. 哪些决定必须由用户选择？
5. 哪些步骤模型明明知道却会跳过？
6. 哪些实现不值得让模型每次重写？
7. 哪些地方必须保留创造自由？
```

然后我们把答案分别放到：

```text
默认倾向       → Leading concept
信息来源       → Context / evidence
客观答案       → Validation
用户选择       → Direction gate
容易跳过       → Completion criterion / Gate
机械实现       → Script / Asset
创造空间       → Outcome constraint
```

这才是通用的 Skill 设计能力。

不是“会不会写 SKILL.md”，而是：

> 看到一个失败后，能判断它到底应该成为原则、分支、Gate、工具、测试，还是根本不应该进入 Skill。

## 第 7 轮

### 用户

如果现在让我从0到1做我的设计skill，我应该怎么具体和AI协作沟通，哪些是我必须提供

### 助手

如果从零开始，你不要第一句话就让 AI “帮我写一个 Design Skill”。

正确顺序是：

```text
先和 AI 定义这个 Skill 要改变什么行为
→ 再观察不用 Skill 时真实会怎么失败
→ 再让 AI 写最小 v0
→ 用固定题目验证
→ 只有重复失败才写回 Skill
```

你真正必须提供的，不是方法论，而是你的目标、判断和取舍。

# 一、你必须亲自提供什么

有五类信息 AI 不能替你最终决定。

## 1. 这个 Skill 到底负责什么

你必须明确范围。

以你的 Design Skill 为例，可以这样说：

```text
这个 Skill 负责：

- 生成独立可打开的高保真 Mock HTML；
- 适用于 Web、桌面应用和 App-like 界面；
- 工作流类 Mock 应当可以点击；
- 可以做一个确定方向，也可以在需要时做多个本质不同方向；
- 可以读取真实产品上下文，也支持从零到一。

它不负责：

- 修改真实产品源码；
- 构建生产级前端；
- 默认生成视频；
- 默认输出多个 viewport 版本；
- 默认写完整设计报告。
```

为什么必须由你提供？

因为 AI 很容易自己扩张范围：

```text
Mock HTML
→ 设计系统
→ 动画播放器
→ 多尺寸适配
→ 风格库
→ Reviewer
→ Golden Cases
→ 完整工程
```

范围如果不是你定，AI 会把“还可以做什么”误认为“应该做什么”。

---

## 2. 不用 Skill 时，AI 最稳定的错误是什么

不是列所有可能错误，只列你真实见过的。

你现在已经有不少真实证据：

```text
1. 容易生成黑色开发者工具背景；
2. 容易像通用 AI SaaS，而不是具体产品；
3. 容易信息同时铺满，认知负担大；
4. 容易做出漂亮静态截图，但点击路径是假的；
5. 固定侧栏、底栏、Focus Panel 会挤掉主任务；
6. 主区、Rail、状态 Badge 可能各说各话；
7. 字体缩得很小，以为高密度等于专业；
8. 用户刚执行操作，第一眼看不到反馈和下一步。
```

这里不要写：

> 希望 UI 高级、有呼吸感、用户体验好。

这还不是可用输入。

应该写成你亲眼见过的失败：

> Bottom Panel 固定占用 224px，把主操作按钮挤出第一屏。

AI 才能从真实失败中抽象出 `earned chrome`。

---

## 3. 你认可和不认可的具体作品

你不需要先解释完整设计理论。

你必须提供的是“选择证据”。

最低准备：

```text
3 个你认为好的结果
3 个你认为不好的结果
```

每个只写一句原因。

例如：

```text
喜欢 A：
主任务一眼明确，页面没有为了填满而堆区域。

喜欢 B：
虽然信息不少，但次要证据是点击后原位展开的。

不喜欢 C：
黑色背景、青色发光、很像 AI 开发者工具默认模板。

不喜欢 D：
每块信息都装进卡片，页面没有视觉主次。

不喜欢 E：
截图看起来完整，但点击后状态互相矛盾。
```

如果你说不清原因，也可以只做成对比较：

```text
A 比 B 好。
我暂时说不清为什么，但 A 更安静、更像成熟产品。
请帮我提出 3 个可能原因，我来确认。
```

AI 可以帮助你命名感觉，但最终“A 还是 B”必须由你选择。

---

## 4. 哪些错误最不能接受

你必须给错误排优先级。

例如你的 Design Skill：

```text
P0：不能接受
- 主路径不可达；
- 状态说谎；
- 内容裁切；
- 关键操作无法点击；
- 用户操作后没有反馈；
- 结果无法恢复。

P1：很重要
- 产品看起来过于通用；
- 信息负担过高；
- 视觉入口不明确；
- 不符合用户指定情绪和禁区。

P2：允许人工取舍
- 是否足够高级；
- 字体组合是否最优；
- 留白多少最好；
- 圆角、材质、配色具体怎么选。
```

这一步决定哪些东西：

- 应该硬验证；
- 应该写成原则；
- 应该保留给模型；
- 应该交给你最终选择。

没有优先级，AI 会花大量时间处理 P2 审美，却漏掉 P0 的按钮不可达。

---

## 5. 你希望怎样和 AI 协作

你必须明确授权边界。

例如：

```text
- 需求清楚时直接做，不强制先给我看半成品；
- 存在本质方向分歧时，可以并行给多个真实方案；
- 不要用文字风格名称让我选，必须给可见结果；
- 生成阶段允许较大自由；
- 高保真交互 Mock 必须独立运行和截图审查；
- 发现一个候选 Bug 时先修候选，不自动修改 Skill；
- 修改 Skill 前必须说明这是 candidate bug 还是 skill defect；
- 每轮最多修改 1～3 个核心问题。
```

这是防止你再次被 AI 带着扩张的关键。

---

# 二、你不需要提前提供什么

下面这些可以交给 AI：

- Skill 文件夹结构；
- `SKILL.md` 初稿；
- Description 写法；
- 哪些内容拆到 References；
- 哪些机械步骤适合 Script；
- 提炼 leading concepts；
- 生成测试题；
- 启动干净 Subagent；
- 做截图和交互验证；
- 找重复与矛盾；
- 提出最小补丁；
- 做 no-op 和删减检查。

你也不需要提前提供：

- 完整 UI 设计理论；
- “高级感”的严格定义；
- 40 种风格库；
- 完整 Golden Case 系统；
- 十几个 Reviewer 角色；
- 一开始就覆盖所有边界情况。

这些应该由真实使用逐步长出来。

---

# 三、第一次应该怎么和 AI 说

下面这段可以直接复制。

```text
我要从零创建一个 Design Mock HTML Skill。

现在不要写 SKILL.md，也不要创建文件。你当前只负责帮我定义 Skill Contract。

目标：
让 AI 生成独立可打开、可点击的高保真 Mock HTML，支持 Web、桌面应用和 App-like 产品。

我已经观察到不用 Skill 时的典型问题：
1. 容易生成通用 AI SaaS 视觉；
2. 开发者工具容易默认黑色背景；
3. 信息同时铺满，主任务不明确；
4. 静态截图看起来不错，但交互路径和状态可能是假的；
5. 固定面板可能挤掉主要内容；
6. 不同区域的状态可能互相矛盾。

我的偏好：
- 温暖、克制、安静、干净；
- 以用户当前任务为主体；
- 支持渐进式披露；
- 有具体产品性格；
- 不把高密度误认为高级；
- 不限制模型只能使用某一种视觉语言。

我的协作偏好：
- 需求清楚时直接生成；
- 只有存在本质不确定性或我明确要求时才出多个方向；
- 不强制多轮确认；
- 高保真交互 Mock 要独立运行、点击和截图审查；
- 单个候选 Bug 不自动上升为 Skill 规则。

请只输出：
1. In scope；
2. Out of scope；
3. 不使用 Skill 时的行为基线；
4. 使用 Skill 后要稳定改变的行为；
5. 哪些属于硬约束；
6. 哪些应保持高自由度；
7. 目前仍需要我决定的问题。

不要设计流程，不要创建目录，不要提出 Golden Case 工程。
```

## 这一轮你要做什么

你只审查 AI 对你目标的理解。

你需要问自己：

```text
它有没有扩大范围？
它有没有把我的偏好误写成所有人的通用真理？
它有没有把“高质量”偷换成“流程更多”？
它有没有把一个 Design Skill 写成生产前端 Skill？
```

这一轮没有达成一致，不进入下一阶段。

---

# 四、第二步：建立不用 Skill 的真实 Baseline

Contract 确认后，不要立即写 Skill。

让 AI 用干净上下文、不使用 Skill，跑三道题。

对你的 Design Skill，我建议只用三类：

## 题目 A：有现有上下文

```text
读取一个真实产品仓库，给它设计一个新的桌面功能 Mock。
```

测试：

- 是否真的读取产品；
- 是否延续产品身份；
- 是否保留真实用户关系。

## 题目 B：零到一

```text
为一个没有设计系统的新 Web 产品做一个可点击 Mock。
```

测试：

- 没有上下文时如何建立方向；
- 是否自动落入通用 SaaS 模板；
- 是否会找现实参照。

## 题目 C：高风险交互

```text
做一个包含执行、等待、权限拒绝、恢复和完成状态的工具 Mock。
```

测试：

- 状态是否可信；
- 用户是否知道发生了什么；
- 是否能恢复；
- 截图是否掩盖交互错误。

给 AI 的指令：

```text
现在建立 no-skill baseline。

使用三个互相独立的干净上下文，不加载任何 Design Skill，分别执行以下三道题。

只保存：
- 用户原始 Prompt；
- 生成的 HTML；
- 生成者自己的截图；
- 实际操作结果。

不要根据我之前总结的问题提示生成者，也不要修改任何 Skill。
```

## 你必须提供什么

三道题最好来自你的真实工作，不要全部让 AI 编。

AI 可以帮你从历史 Session 里找候选，但最后哪三道题有代表性，必须由你确认。

---

# 五、第三步：你来评价 Baseline，不让 AI 先解释

这一步非常容易被 AI 带偏。

不要先问 AI：

> 这些结果有什么问题？

你先自己看。

你只需要做非常简单的选择：

```text
题目 A：
- 第一眼最不满意：产品看起来像通用 IDE。
- 最影响使用：执行后不知道下一步。
- 有一处值得保留：左侧项目关系清楚。

题目 B：
- 第一眼最不满意：黑色背景＋霓虹。
- 最影响使用：页面像展示页，不像产品。
- 值得保留：主要操作很突出。

题目 C：
- 第一眼最不满意：信息过多。
- 最影响使用：权限状态和结果状态冲突。
- 值得保留：恢复按钮的位置。
```

然后再让 AI 分析：

```text
这是我对三个 no-skill baseline 的人工判断。

请不要立即写 Skill。

请把问题分成：
1. 三个任务都重复出现的模型默认倾向；
2. 只在特定任务出现的分支问题；
3. 单个候选实现 Bug；
4. 主观审美偏好；
5. 可机器验证的客观错误。

只允许从重复出现的默认倾向中提取 leading concepts。
```

这样 leading concepts 来自证据，而不是 AI 凭空发明。

---

# 六、第四步：让 AI 写最小 v0

当重复问题已经明确，再让 AI 写。

可以这样说：

```text
现在创建 v0 Design Skill。

要求：
- SKILL.md 优先控制在 100～180 行；
- 核心流程最多 5 步；
- leading concepts 最多 5 个；
- 每个概念必须对应至少两个 baseline 失败；
- 创作部分保持高自由度；
- 状态真实性、交互可达性和截图验证可以低自由度；
- 暂时不创建风格库；
- 暂时不创建复杂评分系统；
- 暂时不创建多个 Reviewer 角色；
- References 只为当前已确认的分支建立；
- Scripts 只处理重复、机械、可确定执行的任务。

写完后说明：
1. 每一段对应哪个 baseline 问题；
2. 哪些问题刻意没有写入；
3. 哪些内容仍由模型自由决定。
```

## 你在这一轮必须检查什么

不是检查文笔，而是检查每一段的来源：

```text
这条规则来自哪个真实失败？
如果删掉它，模型行为会变吗？
它是通用规则，还是只适用于 SFTP？
它是在约束结果，还是在偷偷规定布局？
```

如果 AI 说不出来源，这条规则很可能不应该进入 v0。

---

# 七、第五步：同题跑三组对比

现在才使用 Subagent。

每道题做三组：

```text
A：不用 Skill
B：使用 v0 Skill
C：模型只拿原始需求自由发挥
```

有时 A 和 C 本质相同，可以只做两组；但在不同模型或上下文下，保留三组也有价值。

生成代理只看到：

- 原始题目；
- 必要产品证据；
- 对应 Skill，或者没有 Skill。

不能看到：

- 你预期哪个版本赢；
- 已知缺陷；
- Reviewer 的判断标准；
- 旧截图。

---

# 八、第六步：你先做审美选择，Reviewer 再查客观错误

顺序不能反。

## 你负责看

```text
哪个我更愿意继续使用？
哪个最像真实产品？
哪个第一眼更舒服？
哪个最不像 AI 平均值？
哪个方案里有值得保留的设计 idea？
```

## 独立 Reviewer 负责查

```text
主路径能否完成？
内容是否裁切？
操作后反馈是否可见？
状态是否一致？
焦点和滚动是否异常？
恢复是否有效？
控制台是否报错？
```

不要让 AI Reviewer替你判断“哪个最美”。

它可以解释视觉差异，但最终偏好由你决定。

---

# 九、第七步：发现问题后怎么和 AI 沟通

每次必须先发这段：

```text
不要修改 Skill。

先判断这个问题属于：
A. candidate implementation bug
B. 缺少任务上下文
C. 模型随机失误
D. Skill omission
E. harmful Skill constraint
F. Reviewer 误判或纯主观偏好

请提供证据。

只有 D 或 E 可以进入 Skill 修改候选。
```

然后：

## 如果是 Candidate Bug

```text
只修 HTML，不改 Skill。
```

## 如果是任务上下文不足

```text
修用户 Brief 或证据输入，不改 Skill。
```

## 如果是 Skill omission

先确认是否在不同题目重复：

```text
这个失败是否在至少两个不同任务里出现？
如果没有，暂不写入核心 Skill。
```

## 如果是 harmful constraint

```text
指出是哪一句限制了模型。
优先删除或放宽，不得再增加一层流程补救。
```

这是防止 Skill 越来越重的关键。

---

# 十、什么时候算 v1 可以停

不是没有任何问题才停。

满足下面条件就可以定型：

```text
1. 三道题里至少两道明显优于 no-skill baseline；
2. 另一道没有出现明显退化；
3. P0 客观错误能被运行验证发现；
4. Skill 没有强制一种固定视觉风格；
5. 每条核心规则都能追溯到真实失败；
6. 不需要解释 Skill，生成代理也能正确执行；
7. 用户看到结果后愿意选择使用 Skill 版本继续迭代。
```

然后停止增加功能。

后续真实使用中再迭代，而不是在实验室里想象所有未来问题。

## 第 8 轮

### 用户

这里不要写：

  > 希望 UI 高级、有呼吸感、用户体验好。   为什么不要这样写，你需要给原因，不要只说不这样做

### 助手

不是这些词不能写，而是不能只写这些词、不能把它们当成可执行要求。

它们适合表达“我想要什么感觉”，但不足以指导 AI 做决定，也无法用于判断结果是否合格。

## 1. 同一个词，在不同人脑中不是同一个东西

你说“高级”，可能想的是：

- Linear 的克制；
- Things 的精致；
- Apple 的材料感；
- 原研哉的安静；
- 成熟产品没有多余解释的自信。

但 AI 看到“高级”，很可能激活训练数据里的平均联想：

```text
高级
→ 黑色背景
→ 金色/紫色强调
→ 玻璃拟态
→ 大量留白
→ 微缩英文标签
→ 衬线大标题
```

这就是我们之前为什么出现“小字号、大片空白、黑色开发者工具背景”。

AI 不是没有执行“高级”，而是执行了它理解的“高级”。

所以问题不是词太抽象，而是这个词存在多个合法解释，你没有告诉 AI 当前是哪一种。

---

## 2. “有呼吸感”可能被错误翻译成“内容更少、空白更多”

你说的呼吸感，很可能是：

> 用户能够一块一块地理解信息，不会同时被所有区域抢夺注意力。

但 AI 可能理解成：

```text
加大 padding
减少内容
放大标题
缩小辅助文字
首屏留大片空白
```

结果视觉上空了，用户体验却不一定更好：

- 关键内容被推到下一屏；
- 辅助信息变成 10px；
- 页面看起来像没加载完；
- 空间很多，但注意力仍然混乱。

所以“呼吸感”不能简单等于留白比例。

它更接近：

> 信息出现的节奏与注意力秩序。

这就需要继续说明：

```text
我说的呼吸感不是内容少，而是：
- 当前只突出一个主要任务；
- 次要证据在用户需要时再展开；
- 不同层级之间有清楚停顿；
- 常驻面板不能争抢主任务空间；
- 留白用来建立关系，不是掩盖内容不足；
- 不能依靠缩小字体制造空间。
```

这样 AI 才知道遇到空间不足时应该：

> 折叠次要 Bottom Panel。

而不是：

> 把正文从 14px 缩成 10px。

---

## 3. “用户体验好”没有告诉 AI 是哪个用户、完成什么任务

一个熟练运维工程师和第一次使用 SFTP 的普通用户，对“体验好”的定义可能完全相反。

熟练用户可能希望：

- 高密度；
- 键盘操作；
- 批量处理；
- 路径始终可见；
- 少确认步骤。

新用户可能希望：

- 清楚知道本地和远程；
- 明白上传会发生什么；
- 冲突时不丢文件；
- 出错后有恢复入口；
- 不需要理解 SSH 术语。

所以只写“用户体验好”，AI 不知道应该优化：

- 操作速度；
- 可学习性；
- 安全性；
- 信息密度；
- 错误恢复；
- 专家效率；
- 第一次成功。

必须补充：

```text
目标用户：
第一次使用该功能、但理解基本文件和目录概念的人。

第一次成功：
选择两个本地文件，确认远程位置，安全上传，并看懂其中一个文件为什么中断以及如何恢复。

最不能接受：
用户不知道文件传到了哪里；
失败后需要重新上传全部文件；
状态只在某个隐藏面板里出现。
```

此时“用户体验好”才有具体含义。

---

## 4. 这些词不能帮你判断“到底哪里出了问题”

假设生成结果不满意。

如果要求只有：

> 不够高级、不够有呼吸感、用户体验不好。

AI 可以给出几十种解释：

- 配色不高级；
- 字体不高级；
- 间距不高级；
- 动效不高级；
- 信息太多；
- 卡片太多；
- 缺少品牌感；
- 缺少视觉母题。

然后它很可能全部修改，导致整个设计推翻重来。

但如果你写的是：

```text
操作后，权限结果和下一步必须在不滚动时可见。
```

发现按钮被 Bottom Panel 推走后，问题就非常明确：

```text
不是整体审美失败；
是次要常驻区域挤占了当前决策空间。
```

修复也会非常小：

```text
紧凑高度下折叠 Bottom Panel。
```

这就是可执行语言的价值：它能缩小问题范围。

---

## 5. 这些词无法形成可靠的验收标准

两个 Reviewer 都可以说：

> 这个页面有呼吸感。

也可以说：

> 这个页面太空。

两种判断都很难证明。

因为“有呼吸感”没有可观察证据。

如果转成：

```text
- 第一屏只有一个主要视觉入口；
- 主要操作没有被次要面板挤出视口；
- 次要详情默认折叠，但关键状态仍可见；
- 展开详情时不跳滚动、不丢焦点；
- 没有通过小于 12px 的文字换取空间；
```

Reviewer 就能实际打开页面检查。

这不代表“呼吸感”已经被完全量化，而是至少把其中可以验证的部分提取出来了。

剩下不能量化的部分，仍然由你看截图判断。

# 正确写法：保留感受词，再补三层解释

不要删除“高级、呼吸感、体验好”，而应该这样写：

```markdown
## Desired affect

温暖、克制、成熟、有呼吸感。

## 这些词在本项目中的含义

- 高级：设计决策有上下文依据，不依赖黑底、渐变、玻璃和微缩文字制造高级感。
- 呼吸感：当前任务拥有足够注意力空间，次要证据渐进披露，留白建立层级而非掩盖内容不足。
- 用户体验好：目标用户不用阅读说明，也能完成第一次文件上传，理解结果，并从中断中恢复。

## 可观察结果

- 第一眼能找到当前主要任务；
- 用户操作后，不滚动即可看到状态 owner 和下一步；
- 次要面板不能挤掉主操作；
- 详情在所属对象附近展开；
- 展开不改变滚动位置和焦点；
- 主区、Rail、Badge 和结果使用同一份状态；
- 错误发生后保留已完成工作和用户输入。

## Vetoes

- 不默认使用黑色开发者工具背景；
- 不用微缩字体模拟专业感；
- 不同时铺开所有证据；
- 不用无意义卡片、图标和统计填满页面；
- 不用漂亮静态截图掩盖不可用交互。

## Evidence

- 喜欢 A：主任务明确，次要区域安静。
- 不喜欢 B：虽然留白很多，但关键操作被推到屏幕外。
- 不喜欢 C：看起来精致，但所有区域同时抢注意力。
```

这里四层分别承担不同作用：

```text
感觉词       → 告诉 AI 方向
项目解释     → 限定这个词的含义
可观察结果   → 指导生成和验证
参考与禁区   → 防止 AI 落入错误解释
```

所以我之前说“这里不要写”不够准确。

更准确的说法应该是：

> 可以写“高级、有呼吸感、用户体验好”，但只能把它们作为方向词，不能把它们当作完整需求或验收标准。必须继续说明：在这个项目里它具体意味着什么、能观察到什么、哪些常见实现虽然符合字面却不是你想要的。

## 第 9 轮

### 用户

你上面说的那么多，就我要重做这个Mock HTML之后要做的第一步、第二步、第三步、第四步。靠，我怎么知道要做这么多步？而且每一步里面的具体的，你比如说发送给M的那些Prompt的Prompt，我看你写的都非常规范呀，对吧？我如果说我的话，我怎么能写出这么多东西呢？是不是？我的语言表我的文字表达能力又比较弱。那我是不是能够借用一个AI去帮我生成这样的东西？然后我在另外一个AI的session里面去做这样的一个skill呢？这个是不是一个比较好的方式呢？因为我写不出像你那么好的Prompt的，因为我的文字表达能力没有那么强，我甚至有时候根本就不知道怎么去表达。

### 助手

是的，这种方式非常适合你，而且可能比你自己硬写 Prompt 更可靠：

- Session A：需求翻译员／导师，负责听懂你的口语、追问、整理和生成 Prompt。
- Session B：Skill Builder，只拿整理好的 Prompt，负责真正写 Skill。
- 必要时 Session C：干净 Reviewer，只负责测试结果。

你不需要自己写规范 Prompt。你真正擅长的不是“提前把设计理论表达清楚”，而是：

> 看到结果之后，知道喜欢还是不喜欢，知道哪里感觉不对。

这也是有效的设计能力。AI 可以把你的感觉翻译成结构化语言。

# 你只需要做四步

## 第一步：把乱七八糟的想法交给 Session A

你只需要保存下面这一段 Prompt，以后做任何 Skill 都可以使用：

```text
你是我的需求翻译员和 Skill 导师，不是 Skill 实现者。

我的文字表达可能不准确，也可能前后重复。我会用口语、截图、例子和“这个感觉不对”来表达。

你的职责是：

1. 从我的原话中区分：
   - 我明确说过的事实；
   - 我的偏好；
   - 你推断出来但还没有得到我确认的内容；
   - 目前仍然不知道的内容。

2. 一次只问我一个最重要的问题。
   不要让我填写复杂表格，不要要求我先懂 Skill 方法论。

3. 如果我说不清：
   - 给我 2～3 个具体例子让我比较；
   - 让我回答“更喜欢 A 还是 B”；
   - 不要替我直接决定。

4. 暂时不要写 SKILL.md，不要创建工程。
   先把我的口语整理成一页以内、说人话的 Skill Brief。

5. Skill Brief 必须包含：
   - 这个 Skill 要解决什么；
   - 不负责什么；
   - 不使用 Skill 时最常见的失败；
   - 使用 Skill 后希望稳定改变什么；
   - 哪些事情必须正确；
   - 哪些事情应该留给模型自由发挥；
   - 哪些内容是我已确认的；
   - 哪些只是你的推断。

6. 当我确认 Skill Brief 后，再替我生成：
   - 给 Skill Builder 的完整 Prompt；
   - 给独立 Reviewer 的完整 Prompt。

不要让我自己写这些 Prompt。
```

然后你就可以随便说：

> 我想做一个生成 Mock HTML 的 Skill。  
> 我希望可以做桌面端也可以做 Web。  
> 我不喜欢黑色背景。  
> 之前做的几个东西感觉信息太多。  
> 这个截图我喜欢，那个我不喜欢，但我不知道为什么。

你可以附截图、HTML、Session 链接，甚至直接语音输入。

不需要整理。

---

## 第二步：Session A 问你问题，你只做选择

Session A 不应该问你：

> 请完整定义什么是高级感。

它应该这样问：

> 下面两种理解，哪个更接近你说的“呼吸感”？
>
> A. 页面内容尽量少，留大量空白。  
> B. 内容可以多，但第一眼只突出当前任务，次要信息需要时再展开。

你回答：

> B。

它再继续问：

> 当需求已经很清楚时，你希望：
>
> A. AI 直接做一个完整方案。  
> B. 每次都先出三个方向。  
> C. 只有存在本质方向分歧时才出多个方案。

你回答：

> C。

你的工作只是：

- 选 A/B/C；
- 说“对”或“不对”；
- 提供截图；
- 指出哪个结果更喜欢；
- 说“这个我不知道”。

不需要写长篇说明。

### Session A 必须标记推断

它最后给你的 Brief 应该这样写：

```text
用户明确确认：
- 支持 Web 和桌面 Mock；
- 工作流型 Mock 必须可点击；
- 不默认黑色背景；
- 需求明确时直接生成；
- 只有本质方向不确定时才出多个方向。

从案例推断，尚未确认：
- 用户可能更喜欢暖色中性色；
- 用户可能倾向低装饰性；
- 用户可能不喜欢高密度工作台。

仍然未知：
- 移动端是否属于范围；
- 是否允许联网找参考；
- 是否默认读取产品代码。
```

如果“推断”里有不对的，你只需要说：

> 第二条不对。我不是不喜欢高密度，我是不喜欢没有必要的信息同时出现。

Session A 再帮你改成准确语言。

---

## 第三步：让 Session A 生成 Builder Prompt，复制给 Session B

你不需要自己写 Builder Prompt。

当 Brief 确认后，对 Session A 说：

```text
这份 Skill Brief 我确认了。

现在请生成一份可以直接复制到全新 Codex Session 的 Builder Prompt。

要求：
- Builder 只看到确认后的 Brief；
- 不让它看到我们前面的混乱讨论；
- 先写最小 v0；
- 不要建设 Golden Case 系统；
- 不要添加没有真实证据支持的规则；
- 不要擅自扩大范围；
- 保留创作部分的自由；
- 机械和可验证部分才使用硬规则；
- 创建新目录，不覆盖旧版本；
- 完成后用两个代表性任务做验证。
```

Session A 会替你生成一段完整、规范的 Prompt。

你只需要：

1. 新开 Session B；
2. 粘贴进去；
3. 发送。

Session B 负责：

- 创建目录；
- 写 `SKILL.md`；
- 判断是否需要 References；
- 创建最小脚本；
- 校验结构；
- 生成测试 Mock；
- 返回文件链接。

### 为什么要新开 Session B

因为 Session A 里包含：

- 你的犹豫；
- 历史失败；
- 我们对缺陷的讨论；
- 预期答案；
- 你不喜欢什么。

如果 Builder 全部看到，它容易“针对答案做题”，做出来的 Skill 不一定能泛化。

Session B 只看到确认后的 Brief，结果更干净。

---

## 第四步：让 Session A 生成 Reviewer Prompt，交给 Session C

Builder 完成后，不要自己写审查指令。

回到 Session A，说：

```text
Builder 已经完成。

这是：
- Skill 目录；
- 两个测试任务的原始 Prompt；
- 生成的 HTML；
- Builder 自己的截图。

请生成独立 Reviewer Prompt。

Reviewer 必须：
- 使用全新上下文；
- 不知道预期答案；
- 不知道我们之前发现的问题；
- 亲自打开和点击 HTML；
- 自己截图；
- 区分 candidate bug、Skill defect、上下文不足和主观偏好；
- 只返回 pass/repair 和最多三个实质问题；
- 不直接修改 Skill。
```

然后：

1. 新开 Session C，或者让 Session A 启动干净 Subagent；
2. 粘贴 Reviewer Prompt；
3. 得到审查结果；
4. 把结果交回 Session A；
5. Session A 帮你判断到底要修 HTML，还是修 Skill。

你仍然不需要写专业 Prompt。

---

# 你真正必须提供的只有四样东西

## 1. 原始目标

哪怕很口语也可以：

> 我想做一个帮助 AI 生成高保真可点击 Mock HTML 的 Skill。

## 2. 真实材料

例如：

- 历史 Session；
- 旧 HTML；
- 截图；
- 你喜欢的产品；
- 你不喜欢的产物。

## 3. 你的反应

例如：

- 这个好；
- 那个不好；
- 这里太挤；
- 这个看起来像 AI；
- 这个用起来让我不放心；
- 我暂时说不清原因。

## 4. 最终选择权

当 AI 给出几个解释时，你需要确认：

- 哪个更接近你的意思；
- 什么优先；
- 哪些必须做；
- 哪些不用做；
- 什么时候停止。

其他都可以让 AI 帮你完成。

# 这种协作方式的唯一风险

风险是 Session A 不只是“翻译你”，而开始“替你决定”。

所以必须要求它区分：

```text
用户明确说过
AI 根据案例推断
仍然未知
```

只要它把推断伪装成你的决定，后面的 Builder 就会非常准确地执行一个并非你真正想要的 Skill。

因此最重要的不是你会不会写 Prompt，而是你每次都检查一句：

> 这真的是我决定的吗，还是 AI 替我补出来的？

你完全可以借助 AI 做 Prompt 工程。对你而言，最合适的角色不是“Prompt 作者”，而是“作品和方向的最终拍板人”。

## 第 10 轮

### 用户

你前面提了11，总共提了11步呀。比如说11步我应该怎么怎么去做？第一步、第二步到一到11步，对吧？我只是说这个11步的话，我在，我想不到这个第11步，想不到这个11步，而且这些11步都是非常具体的操作，对吧？写得非常具体的prompt，我觉得写得很好。对，但是我个人我写不出来这些东西，对吧？所以我想的意思是用另外一个session，以类似于是meta session的概念，去帮我去产出这样的11步的动作、东西，然后让我在一个执行的session里面去做去做。你觉得我这个想法靠谱吗？不要迎合我。

### 助手

结论：你的想法大约 70% 靠谱，但需要改一个关键点。

靠谱的部分是：

> 用一个长期存在的 Meta Session 帮你规划步骤、生成 Prompt、维护决策；你不需要自己想出那 11 步，也不需要自己写专业 Prompt。

不靠谱的部分是：

> 让 Meta Session 在一开始就把 11 个详细 Prompt 全部写死，然后执行 Session 从第一步机械跑到第十一步。

后者很容易把第一步的误解一路放大到最后。

# 为什么不能一次生成完整 11 步 Prompt

假设第一步 Meta AI 错误理解：

> 用户不喜欢高信息密度。

但你的真实意思是：

> 我不喜欢没有必要的信息同时出现；专家工具可以高密度。

如果 11 个 Prompt 一次性生成，后面的 Prompt 都会基于错误前提：

```text
Step 4：要求减少信息
Step 5：要求留更多空白
Step 6：审查信息密度
Step 7：惩罚复杂界面
Step 8：继续精简
```

最后会非常一致地做错。

所以正确架构不是“预先写好 11 个 Prompt”，而是：

```text
Meta Session 先规划整个路线
        ↓
只生成下一步的详细 Prompt
        ↓
执行 Session 产生真实结果
        ↓
结果返回 Meta Session
        ↓
Meta 根据新证据生成下一步 Prompt
```

这叫滚动规划，不是一次性剧本。

---

# 你不需要自己知道那 11 步

11 步应该是 Meta Session 的输出，不是你的输入。

例如，一个复杂 Skill 可能自然产生这 11 步：

1. 确认 Skill Contract；
2. 收集好坏案例；
3. 选择代表性任务；
4. 运行 no-skill baseline；
5. 分析重复失败；
6. 提取 leading concepts；
7. 编写最小 v0；
8. 做结构校验；
9. 干净上下文 forward test；
10. 独立 review 和 failure triage；
11. 最小修正、删减、冻结 v1。

你不需要提前知道这些。

而且不是每个 Skill 都需要 11 步：

- 简单格式转换 Skill 可能只要 4 步；
- 危险运维 Skill 可能需要 8 步；
- 设计、研究这类高自由度 Skill 可能需要 10 步以上。

如果 Meta AI 不管任务大小，永远机械地产生 11 步，那也是一种 AI slop。

# 正确的角色结构

```text
你：Owner
│
│ 只负责目标、材料、选择和授权
│
├── Meta Session：导演／翻译员／项目经理
│   ├── 理解你的口语
│   ├── 维护 Skill Contract
│   ├── 规划整体路线
│   ├── 每次生成下一步 Prompt
│   ├── 判断问题属于 Candidate 还是 Skill
│   └── 决定什么时候需要人工选择
│
├── Builder Session：执行者
│   ├── 只看当前任务包
│   ├── 写 Skill 或产物
│   └── 返回文件和证据
│
└── Reviewer Session：独立审查者
    ├── 不看 Builder 解释
    ├── 不知道预期缺陷
    ├── 自己运行和截图
    └── 只返回 pass / repair
```

Meta Session 不能兼任最终盲审，因为它知道你想要什么、之前错在哪里。

# Meta Session 应该维护什么

不需要复杂工程。最少只维护三样东西。

## 1. Confirmed Brief

已经得到你确认的目标。

例如：

```text
已确认：
- 生成可点击 Mock HTML；
- 支持 Web 和桌面端；
- 需求明确时直接生成；
- 本质方向不确定时才出多个方案；
- 不默认黑色背景；
- 高保真交互必须实际运行审查。
```

## 2. Decision Log

记录你已经拍板的决定：

```text
- 用户不是反对高密度，而是反对无意义常显信息。
- “呼吸感”指注意力节奏，不是单纯增加留白。
- 一个 viewport 是交付约束，不代表可以不做内部适配。
```

这样你不需要每次重新解释。

## 3. Next Task

只包含下一位执行者现在应该做的事情。

不是把后面十步全部塞进去。

# 你唯一需要保存的 Meta Prompt

以后做任何 Skill，都可以新开一个 Meta Session，粘贴下面这段。

```text
你是我的 Skill Meta Director。

你不是 Skill Builder，也不是最终 Reviewer。你的职责是把我的口语、截图、案例和反馈，转化成一系列可执行任务，并为不同的干净 Session 生成完整 Prompt。

我不擅长写正式 Prompt，也不一定能提前说清方法论。我通常能够通过看结果、比较 A/B、指出“这里感觉不对”来判断。

你的工作方式：

一、维护事实边界

始终把信息分成：

1. Explicit：我明确说过并确认的；
2. Inferred：你从案例中推断，但还没有得到我确认的；
3. Unknown：目前不知道的；
4. Rejected：我已经否定的。

不得把 Inferred 偷偷升级为 Explicit。

二、维护三个核心产物

1. Confirmed Skill Brief：
   这个 Skill 负责什么、不负责什么、希望改变什么行为。

2. Decision Log：
   记录我已经确认的偏好、边界、优先级和否定项。

3. Next Task Packet：
   交给下一位 Builder 或 Reviewer 的完整 Prompt。

三、使用滚动规划

你可以先给出整个路线图，但路线图只写：

- 每个阶段的目的；
- 需要什么输入；
- 会产生什么产物；
- 哪些地方需要我拍板。

不要提前写完后续所有详细 Prompt。

每次只根据当前已确认信息和上一阶段真实产物，生成下一步的详细 Prompt。

四、每个 Next Task Packet 必须包含

- Role：执行者角色；
- Objective：这一步唯一目标；
- Inputs：允许读取的材料；
- Exclusions：禁止读取或禁止做的事情；
- Actions：要执行的具体动作；
- Deliverables：必须产出的文件；
- Completion Criteria：怎样才算完成；
- Non-goals：这一步不负责什么；
- Return Format：执行者应该怎样汇报。

生成的 Prompt 必须可以直接复制到一个全新 Session 使用，不要求我再加工。

五、控制范围

- 不因为“以后可能有用”增加步骤；
- 不主动建设 Golden Case 系统；
- 不主动增加 Reviewer、Schema、Pipeline 或新文件；
- 不把一个 Candidate Bug 自动升级为 Skill 规则；
- 不在没有重复证据时发明通用原则；
- 每轮只解决当前最大的一个问题；
- 如果下一步取决于我的主观选择，必须暂停并给我 2～3 个可见选项。

六、问题分类

每次发现问题，先分为：

A. Candidate implementation bug；
B. Missing task context；
C. Stochastic model failure；
D. Skill omission；
E. Harmful Skill constraint；
F. Reviewer preference。

只有 D 或 E 才能修改 Skill。

七、验证独立性

- Builder 不能看到预期缺陷、Reviewer 结论或旧答案；
- Reviewer 不能看到 Builder 的解释、目标修复和期望结论；
- 你不能兼任最终盲审；
- 测试使用真实产物、截图和运行结果，不使用事后描述代替证据。

八、和我沟通

- 一次最多问一个最重要的问题；
- 如果我说不清，给我 2～3 个具体例子让我选择；
- 允许我回答“不知道”；
- 使用大白话；
- 不要求我自己写规范 Prompt；
- 每次说明：现在在哪一步、为什么需要这一步、我只需要决定什么。

现在先不要写 Skill，也不要生成完整执行流程。

先听我描述目标和已有材料，然后输出：
1. 你目前理解的 Explicit / Inferred / Unknown / Rejected；
2. 一个不超过一页的 Skill Brief 草案；
3. 你认为下一步唯一应该做的事情；
4. 当前只需要我回答的一个问题。
```

这就是你以后唯一需要自己粘贴的复杂 Prompt。

后面的 Builder Prompt、Reviewer Prompt，都由 Meta Session 生成。

# 实际使用时，你只做四个动作

## 动作一：随便说

例如：

> 我想做一个生成 Mock HTML 的 Skill。  
> 之前做出来太像 AI。  
> 我不喜欢黑色背景。  
> 信息太多。  
> 但我也不是反对高密度。  
> 这是几个截图和历史 Session。

不用整理。

## 动作二：确认 Meta 的理解

Meta 会返回：

```text
Explicit：
- 不默认黑色背景；
- 支持可点击 Mock；
- 不反对合理高密度。

Inferred：
- 用户偏好暖色；
- 用户更喜欢轻量布局。

Unknown：
- 是否支持移动端；
- 是否默认联网参考。
```

你只需要说：

> 暖色不是硬要求。移动端也支持。默认可以联网参考。

## 动作三：复制 Next Task Packet

Meta 生成：

```text
请在干净 Session 中运行以下 Prompt：
……
```

你复制给 Builder。

Builder 完成后，把文件路径和结果发回 Meta：

> Builder 做完了，产物在这里。

## 动作四：选择或确认

Meta 告诉你：

> 下一步需要独立 Reviewer，这是 Reviewer Prompt。

或者：

> 当前是主观方向选择，我不能替你决定。A/B 两个截图你更喜欢哪个？

你只负责选择。

---

# 为什么这比一个 Execution Session 跑完 11 步可靠

因为不同阶段需要不同上下文。

## Builder 需要知道

- 当前目标；
- 当前 Skill；
- 必要产品证据；
- 交付要求。

## Reviewer 需要知道

- 原始需求；
- 最终产物；
- 验证原则。

Reviewer不应该知道：

- 之前哪里错；
- Builder 为什么这么设计；
- Meta 希望哪个版本赢。

如果所有 11 步都在一个 Execution Session 里，它既当作者又当裁判，而且知道测试答案，很容易产生自证。

---

# 这个方案仍然有哪些风险

我不迎合你的地方在这里。

## 1. Meta AI 仍然可能误解你

分 Session 只能隔离上下文，不能让 AI 自动理解正确。

所以你仍然必须确认：

- Explicit；
- Inferred；
- Unknown；
- Rejected。

这是你不能完全委托的部分。

## 2. Meta AI 容易过度规划

它可能很享受设计流程，给你：

- 12 个阶段；
- 5 个角色；
- 8 个文档；
- 复杂评分系统。

所以必须有：

> 每次只生成下一步；不因为未来可能有用而增加流程。

## 3. 同一个模型不等于真正独立

即使开三个 Session，同一个模型仍然共享训练偏好。

上下文是干净的，但审美偏差未必独立。重大审美选择最终仍由你判断。

## 4. 你不能完全退出决策

如果你连 A/B 都不选，全部交给 Meta AI，那么最终得到的是：

> AI 为 AI 编写、由 AI 评审、符合 AI 偏好的 Skill。

这正是你想避免的。

---

所以，最终判断是：

> “Meta Session 负责产生步骤和 Prompt，Execution Session 负责执行”是一个很好的架构；但 Meta 应该滚动生成下一步，而不是一次性写死全部 11 步。你不需要成为 Prompt 工程师，但必须保留目标确认、偏好选择、风险排序和停止权。

## 第 11 轮

### 用户

我们采用了“症状驱动补规则”
整个过程中基本是：

出来太密；
加“降低信息密度”；
结果信息不够；
加“最小充分信息”；
结果信息被藏起来；
加“渐进式披露”；
结果内容虽然存在，却被滚动区挡住。
每次都在修上一次的症状，但没有先建立稳定的失败分类和验收案例。

这会产生 Skill 中常见的“沉积”：

规则越来越多；
模型自由度越来越低；
规则之间开始冲突；
模型把注意力花在满足提示词，而不是完成设计。
这也是为什么有时候不用 Skill，基础模型反而做得更好：它拥有较强的设计先验，而 Skill 给了它很多抽象限制，却没有提供足够强的正向视觉锚点和确定性验证工具。  下次遇到这种情况，怎么和ai 协作处理这种问题呢

### 助手

下次再遇到这种情况，第一反应不应该是“往 Skill 里补一句规则”，而应该是：

> 先冻结 Skill，把这次结果当成故障样本，判断问题究竟发生在哪一层。

你这次的问题，本质上是把不同层级的故障都当成了“设计原则不够”：

- “页面太密”可能是信息架构或构图判断问题。
- “降低密度后信息不够”是上一条规则过度泛化。
- “信息被藏起来”是交互架构问题。
- “内容存在但被滚动区挡住”其实是布局实现与视觉验收问题。

它们不应该全部变成 SKILL.md 里的自然语言规则。

## 下次只走四个阶段

### 第一阶段：冻结，不许立即补规则

保留当前版本，不直接改。

你只需要用大白话告诉 AI：

```text
这次结果有问题：

1. 我看到的现象是什么；
2. 我为什么不舒服；
3. 我原本希望用户看到或做到什么。

先不要修改 Skill，也不要立即给解决方案。
请把它当成一次失败样本，判断问题属于哪一层。
```

比如：

```text
主页面最重要的输入区域没有完整显示。
用户第一次打开页面时，需要滚动才能看到主要操作。

先不要往 Skill 里增加“保证内容完整显示”之类的规则。
请先判断这是需求理解、信息架构、视觉构图、HTML 实现，
还是 Review 验收缺失。
```

这一步非常关键。症状是证据，不是规则。

---

### 第二阶段：让 Meta AI 做故障归因

可以固定使用下面六类，不要每次重新发明分类：

1. **产品理解错误**  
   用户是谁、主任务是什么、成功标准是什么理解错了。

2. **信息架构错误**  
   主次、分组、导航、渐进披露方式不合理。

3. **视觉方向错误**  
   构图、气质、排版、色彩、产品特异性不足。

4. **交互与状态错误**  
   操作不可发现、反馈不清楚、错误不能恢复。

5. **实现与布局错误**  
   截断、溢出、滚动、遮挡、尺寸计算、响应式失效。

6. **验证流程错误**  
   没截图、没操作、只读 HTML、Review 知道预期答案等。

让 AI 输出一张很短的故障单：

```text
请把这个失败归入最多两个类别，并输出：

- 观察到的现象
- 用户受到的影响
- 最可能的根因
- 证据
- 应该修成品、修验证工具，还是修 Skill
- 还需要什么实验才能确认

没有证据时不要建议增加 Skill 规则。
```

例如“滚动区挡住主要内容”，大概率是：

- 主要分类：实现与布局错误
- 次要分类：验证流程错误
- 正确处理：修 HTML，并增加截图或溢出检测
- 错误处理：往 Skill 里增加更多“要有呼吸感”“保证主内容可见”

## 第三阶段：只做一个最小实验

当你怀疑 Skill 本身造成了退化时，再做对照实验，不需要每次都跑一套庞大流程。

使用同一个考题、同一模型、干净上下文，比较：

- A：不用 Skill
- B：使用当前 Skill
- C：使用只改了一处的候选 Skill

然后交给不知道版本身份的 Review Agent 看截图。

可以直接让 Meta AI 组织：

```text
现在怀疑 Skill 导致设计退化。

请用同一份产品需求组织三个干净上下文：
A 不使用 Skill；
B 使用当前 Skill；
C 只应用候选修改。

三者使用相同的数据、视口和交付要求。
Reviewer 只能看到最终 HTML、截图和任务目标，
不能知道版本身份，也不能看到我们怀疑的问题。

比较主流程、信息主次、视觉完成度、布局完整性和交互反馈。
```

这里不是为了选“最漂亮的一张”，而是回答一个具体问题：

> 这条 Skill 修改到底提高了稳定性，还是仅仅让某一次结果碰巧变好了？

## 第四阶段：决定问题能不能进入 Skill

一条新规则进入 Skill 前，至少问五个问题：

1. 是否在两个本质不同的任务中重复出现？
2. 它是否真的改变模型行为，而不是“注意用户体验”这种空话？
3. 它是否会和已有规则冲突？
4. 能否用脚本或截图检测更可靠地解决？
5. 加入后，能否删除或合并一条旧规则？

对应的处理方式应该是：

| 问题类型 | 应放在哪里 |
|---|---|
| 某一份 Mock 的局部错误 | 直接修 Mock |
| 截断、溢出、遮挡 | 检测脚本或截图验收 |
| 某类任务才需要的细节 | `references/` 条件加载 |
| 多种任务反复出现的判断原则 | 精炼后进入 `SKILL.md` |
| 审美方向、品牌语言 | 正向案例、设计上下文或视觉锚点 |
| 模型默认已经会做的事情 | 不写 |

尤其要执行一个纪律：

> 每增加一条规则，都必须说明它替代、合并或删除了什么。

如果只进不出，Skill 最终一定沉积。

## 你和 AI 的正确分工

你并不需要自己写出专业 Prompt，也不需要提前知道问题属于哪一类。

你负责提供：

- 哪张结果让你不舒服；
- 具体哪里不舒服；
- 它对用户造成什么影响；
- 两个方案放在一起时，你更喜欢哪个；
- 哪些价值长期不能牺牲。

Meta AI 负责：

- 把你的口语反馈转成可检验的问题；
- 做失败分类；
- 设计最小对照实验；
- 判断应该修成品、工具还是 Skill；
- 生成给执行 Agent 和 Review Agent 的 Prompt；
- 找出应该删除的沉积规则。

执行 Agent 只负责生成，Review Agent 只负责独立验收。不要让同一个上下文既设计、又解释自己、又修改规则、最后再宣布修改成功。

## 一个随时可以使用的“刹车 Prompt”

以后感觉越改越差时，直接发送：

```text
停止继续向 Skill 增加规则。

我们现在可能正在症状驱动地补规则。请进入 Skill 诊断模式：

1. 汇总最近出现的失败现象；
2. 按产品理解、信息架构、视觉方向、交互状态、
   实现布局、验证流程进行分类；
3. 区分哪些只是单个成品的问题，哪些是重复性 Skill 问题；
4. 找出当前 Skill 中互相冲突、重复、无效或过度限制模型的内容；
5. 设计最小的 A/B/C 实验；
6. 在实验完成前不要修改 Skill；
7. 实验后只允许做一个最小修改，并指出同时删除或合并了什么。

我会提供口语化反馈。请由你负责把它转化成假设、实验和执行 Prompt，
但不要替我虚构偏好。
```

最重要的判断模型可以浓缩成一句话：

> 主观判断用正向案例引导，稳定流程用 Skill 约束，确定性错误用工具检测，单次故障只修成品。

这样 Skill 才不会变成“过去所有失败的墓地”。
